# 本地部署与公开发布

仅在用户要求安装、更新或发布 Skill 时使用。发布的对象是通用技能，不是私人知识库。用户要求“部署”时先识别它指技能安装、vault 配置还是服务；本方案不需要后台进程、端口或云服务器。

## 本地可用与可迁移包

- 检查宿主实际发现的技能路径，复用已验证的安装，不另建同名副本或软链接覆盖。技能发现、规则入口、文件权限和独立新会话是不同验收层。
- 更新前查看工作区未提交改动与远端差异，保护其他编辑；没有自动覆盖/强推步骤。已有库禁止重新运行初始化器。
- 运行单元测试、格式校验和资源检查。测试依赖若需安装，遵循用户授权并隔离于系统环境；不关闭 TLS 校验来绕过安装失败。正常使用本包脚本仅需 Python 标准库。
- 在本地生成可迁移包时，只从审查通过的 Git 提交导出，不递归压缩当前工作目录。导出包不含 `.git`、缓存、环境、备份或真实 vault；保留 `SKILL.md`、相对引用和模板。
- 检查 ZIP 文件清单与提交树逐项一致，解压到独立临时目录跑测试，再计算包的 SHA-256。不要用解压覆盖已安装技能或私人库。

例如，从已审查提交导出（先确认输出目录；尖括号为须替换的参数）：

```sh
git archive --format=zip --prefix=obsidian-agent-brain/ --output="<已确认的包路径>.zip" <已审查提交>
```

## 发布隐私门

1. 当次授权需覆盖目标仓库与公有发布；无法确定发布的是用户资料还是技能时先澄清。公有技能不能包含真实用户偏好、项目/人员、路径、内部端点或接入记录。
2. 审查明确的待提交文件和全部将公开的历史，而不只看 `.gitignore`。检查隐藏文件、软链接、Git 子模块、二进制/附件、真实记忆与备份、凭证特征及作者邮箱。自动模式检查不能证明“没有任何敏感信息”，仍需人工判断候选内容。
3. 使用精确路径暂存，检查 staged diff。提交用现有经确认的公开身份或 GitHub noreply；不要为此修改用户全局 Git 身份。
4. 核对远端分支没有意外变化后正常推送，不强推。遇到冲突先停下合并，不能用本地旧版本覆盖远端。鉴权失败时使用已授权的凭据助手，不从私人记忆中复制 Token 到 URL 或日志。
5. 推送后匿名读取公有仓库的提交及关键文件，核对远端 SHA。需要分发 ZIP 时检查远端归档清单/内容；push 成功不能单独作为匿名可访问或包完整的证据。

只发布通用研究方法与结论，不把某次私人项目的原始研究记录搬进仓库。GitHub 星标、客户端版本等时效信息留核验日期或重新检查，不固化为永久排名/支持保证。

## 从真实升级中沉淀的经验

- 首页按工作意图导航通常比照抄别人的目录更适合已有多项目库；状态留在一份权威项目记忆，视图负责找到它。
- 表格中的 wiki 别名必须转义，目标文件存在不代表显示可用；文件检查与真实阅读视图都要验收。
- 基线哈希变化可提示其他编辑者，不能据此判断其来源，更不能自动回滚。保留最新版并暂停该文件的合并；网盘同步不等于并发控制。
- 用不含隐私的演示条目验证更新读回，明确同会话、独立会话和第二客户端的区别。安装到本地不等于全部客户端自动记忆生效。

私人部署回执记录真实路径、哈希、备份映射及待验证事项；公开仓库只保留通用流程。不要把私人回执一起提交。
